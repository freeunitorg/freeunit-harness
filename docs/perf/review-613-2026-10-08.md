## Finding A (should fix): the assert does not catch a lost flag

build-test.yml:238-245 greps `NXT_HAVE_OPENSSL_VERSION`. `auto/ssltls:69-80` fills that value from
`OpenSSL_version(OPENSSL_VERSION)`. The feature-test program runs that function at configure time,
so the string comes from the library loaded at run time, not from the header. The configure step
sets `LD_LIBRARY_PATH=${OPENSSL35_LIBDIR}` (:225). So the value is "OpenSSL 3.5.9" even when `-I`,
`-L` or the whole `--ld-opt` is lost. The case that matters is a lost `-Wl,-rpath`: unitd then has
no RUNPATH, and every test leg loads the system `libssl.so.3`. That fallback is silent because unitd
needs only `OPENSSL_3.0.0`. I checked this on the laptop: `ldd` on the artifact's unitd, with no slot,
resolves to `/usr/lib/x86_64-linux-gnu/libssl.so.3`. The comment at :238-240 and the commit message
("a lost -I or -L flag would make configure take the runner's system OpenSSL") claim more than the
step checks. This conclusion comes from reading the code. I did not plant a lost flag in CI.
The openssl4 job (:1228-1235) has the same gap, but it runs only the C tests.

Fix: check the binary, not the configure value. After "Make unit" (:251) in the core job, and after
"Unpack the core build" (:569) in the test job:

```yaml
      - name: Assert unitd loads OpenSSL from /opt/openssl-3.5
        run: |
          ldd build/sbin/unitd | grep -E 'lib(ssl|crypto)\.so'
          ldd build/sbin/unitd | grep -q '=> /opt/openssl-3.5/lib[0-9]*/libssl\.so\.3'
```

Keep the configure grep. It still catches a wrong patch level in the slot. Then fix the comment
at :238-240 and the commit message to say what each step checks.
